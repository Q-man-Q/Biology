# База знаний и инженерный опыт агента (Knowledge Base)

> **Назначение документа:** Сводный конспект знаний, архитектурных решений, алгоритмов и практических уроков по устранению сложных сбоев, полученных в ходе разработки и поддержки проекта «ЭкоКарта Заказника Эбита». Предназначен для передачи контекста и использования другими ИИ-агентами в единой базе знаний.

## 1. Профиль проекта и контекст предметной области

* **Название:** «ЭкоКарта Заказника Эбита» (*ebita-boundary-editor / Ebita EcoMap*).
* **Репозиторий:** `Q-man-Q/Biology` (ветка `main`).
* **Публичный URL:** `https://q-man-q.github.io/Biology/`
* **Предметная область:** Экологический мониторинг териофауны (млекопитающих) и биотопов в Государственном природном заказнике «Эбита» (Казахстан / Актюбинская обл.). Включает 13 лесных и степных кварталов (Тереклинский и Эбитинский участки), учет 38 видов млекопитающих (включая виды Красной книги: сайгак, джейран, выдра, каракал, барханный кот) и 15 типов ландшафтных биотопов.
* **Архитектурный стек:**
  * **Frontend:** React 18 (SPA), Vite 5, Tailwind CSS 3, Lucide React (иконки).
  * **ГИС-ядро:** Leaflet 1.9.4 (спутниковые тайлы Google Satellite Hybrid, векторные полигоны, кастомные маркеры, попапы).
  * **Backend / BaaS:** Google Firebase v12 (Cloud Firestore в роли NoSQL базы, Google OAuth 2.0 Auth).
  * **Деплоймент / CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`) с автоматической сборкой и публикацией на GitHub Pages.
  * **Режим работы:** Гибридный Offline-First (локальная работа в степи без интернета + реалтайм облачная синхронизация при появлении связи).

## 2. Ключевые алгоритмы и математический аппарат ГИС

### 2.1. Аффинная геопривязка растровых картосхем к координатам WGS 84
* **Задача:** Перевод процентных координат `[x%, y%]` с архивных бумажных карт-схем в географические координаты `[lat, lng]` (WGS 84) и обратно.
* **Реализация (`src/utils/transformUtils.js`, `src/components/QuarterGisModal.jsx`):**
  * Масштабирование относительно центра `(cx, cy)` с коэффициентами `scaleLat`, `scaleLng`.
  * Применение географических сдвигов `shiftLat`, `shiftLng` относительно базового охвата (lat: 51.00–51.16, lng: 58.05–58.48).
  * Формулы прямого и обратного преобразования (`pctToLatLng`, `latLngToPct`).

### 2.2. Автоматическое вычисление внешнего периметра (`computeOuterBoundaryFromQuarters`)
* **Задача:** Автоматически построить внешний контур ООПТ из набора соприкасающихся полигонов кварталов, исключив внутренние межквартальные границы.
* **Алгоритм (`src/utils/snapping.js`):**
  1. Каждое ребро полигона нормализуется в неупорядоченный ключ `min(k1, k2) | max(k1, k2)`.
  2. Подсчитывается частота встречаемости ребер. Внутренние смежные ребра встречаются $\ge 2$ раз, внешние граничные ребра — строго **1 раз**.
  3. Фильтруются граничные ребра и сшиваются в упорядоченный замкнутый контур через ассоциативный массив смежности `nextMap: k1 -> p2`.

### 2.3. Топологический снайпинг полигонов (`snapQuarterPolygons`)
* **Задача:** Устранить микрозазоры и наложения (slivers) между смежными полигонами кварталов при ручной оцифровке.
* **Алгоритм:**
  1. Кластеризация близких вершин на расстоянии $\le \text{threshold}$ с помощью структуры непересекающихся множеств (Disjoint-Set / Union-Find). Вершины кластера стягиваются в их среднее арифметическое.
  2. Ортогональная проекция висячих вершин на смежные ребра соседей (`pointToSegmentProjection`) с подтягиванием точки к ребру.

### 2.4. Пространственный анализ Point-in-Polygon
* **Реализация (`isPointInPolygon`):** Алгоритм трассировки луча (Ray Casting Algorithm) для определения принадлежности точки встречи животного полигону квартала.

## 3. Критический кейс: Расследование сбоя «Исчезающий интерфейс через 1–2 секунды»

### 3.1. Симптоматика
* Пользователь открывает веб-приложение: 1–2 секунды интерфейс отображается корректно (карта, кнопки, шапка), затем экран мгновенно гаснет, и остается только пустой темный фон (`bg-slate-950`).

### 3.2. Диагностика (Root Cause Analysis)
1. В консоли браузера зафиксирована ошибка:
   `Uncaught DOMException: The quota has been exceeded` (строка бандла, соответствующая `localStorage.setItem`).
2. Во вкладке Network зафиксирован сетевой запрос Firestore:
   `GET firestore channel?gsessionid=...` объемом **4.33 МБ**.
3. **Механизм сбоя:**
   * В веб-браузерах (Chrome, Firefox, Safari) на домен действует жесткий лимит `localStorage` — **ровно 5 МБ** (хранилище синхронное, строковое).
   * Приложение использовало сохранение Base64-фотографий прямо внутри объектов наблюдений. Одно необработанное фото с современного смартфона (5–12 МБ) в Base64 дает 7–16 МБ текста.
   * При старте приложение рендерилось из существующего состояния. Через 1–2 секунды асинхронный слушатель Firestore (`onSnapshot`) получил из облака 4.33 МБ наблюдений.
   * Вызвался хук:
     ```javascript
     useEffect(() => {
       localStorage.setItem('ebita_eco_observations', JSON.stringify(observations));
     }, [observations]);
     ```
   * Объем данных превысил 5 МБ, `localStorage.setItem` выбросил синхронное исключение `DOMException: The quota has been exceeded`.
   * **Поведение React 18:** При возникновении любого необработанного JavaScript-исключения внутри дерева компонентов или `useEffect` при отсутствии `ErrorBoundary`, React **полностью размонтирует всё приложение** из корневого узла `#root`.
   * Контейнер `#root` становился пустым, а так как `<body>` имеет класс `bg-slate-950`, пользователь видел просто темный экран.

### 3.3. Реализованное комплексное решение

1. **Компонент отказоустойчивости [ErrorBoundary.jsx](file:///home/titya/Projects/Biology/src/components/ErrorBoundary.jsx):**
   * Все приложение в `main.jsx` обернуто в классовый компонент `ErrorBoundary` (`getDerivedStateFromError`, `componentDidCatch`).
   * В случае любых непредвиденных сбоев экран никогда не гаснет в пустоту: отображается экран ошибки с выводом деталей и кнопками:
     * «Перезагрузить страницу»;
     * «Очистить кэш» (удаляет поврежденные ключи `localStorage` и перезагружает страницу).
2. **Умное кэширование с защитой от переполнения (Smart Storage Fallback):**
   * Все операции с `localStorage` обернуты в блоки `try...catch`.
   * При возникновении `QuotaExceededError` включается резервный механизм: массив наблюдений очищается от тяжелых Base64-фотографий (`photos.filter(p => !p.startsWith('data:image'))`), сохраняя в локальное хранилище всю текстовую составляющую (координаты, виды, биотопы, заметки).
   * Итог: текстовый кэш занимает ~50–100 КБ вместо 5 МБ, оффлайн-режим сохраняется, а сайт не падает.
3. **Клиентская компрессия изображений перед сохранением:**
   * В `ObservationModal.jsx` добавлено автоматическое масштабирование и сжатие загружаемых с камеры/файла изображений через виртуальный HTML5 Canvas.
   * Параметры: `maxWidth/maxHeight = 1000px`, формат `image/jpeg`, качество `0.7`.
   * Результат: исходные фото 8–12 МБ сжимаются до **80–150 КБ** (в 50–100 раз), не создавая нагрузки ни на `localStorage`, ни на Firestore.
4. **Защитное программирование (Defensive Programming):**
   * Все операции фильтрации, поиска и подсчета статистики переведены на безопасную навигацию и приведение к строке:
     `String(obs.species || '').toLowerCase()`, `String(obs.id || '')`.
   * Исключены падения `Cannot read properties of undefined (reading 'toLowerCase')` при наличии неполных документов в базе.

## 4. Памятка по среде выполнения и специфике песочницы (Agent Sandbox Guidelines)

1. **Безопасность и режим Sandbox:**
   * По умолчанию агент работает в режиме песочницы (`BypassSandbox: false`). В этом режиме сеть отключена, а служебная папка `.git` монтируется только для чтения.
   * Команды, требующие записи в репозиторий (`git add`, `git commit`, `git branch`), а также сетевые команды (`git push origin main`, внешние API) требуют запуска с `BypassSandbox: true` (с подтверждением пользователя).
2. **Стратегия резервного копирования перед рефакторингом:**
   * Перед внесением исправлений в критические модули обязательно:
     1. Создавать изолированный tar-архив кодовой базы в директорию артефактов / scratch:
        `tar --exclude='node_modules' -czf /path/to/scratch/backup.tar.gz .`
     2. Создавать отдельную ветку в Git:
        `git branch backup-before-<task>-<date>`
3. **Диагностика проблем фронтенда без прямого доступа к браузеру:**
   * Анализ переданных пользователем скриншотов консоли и вкладки Network позволяет сразу выявить:
     * Размер ответов API (payload size);
     * Типы DOMException (квоты, безопасность, CORS);
     * Стек вызовов минимизированного бандла.
   * Локальная проверка сборки через `npm run build` гарантирует отсутствие синтаксических ошибок в модулях до отправки коммита.

## 5. Чек-лист для будущих агентов при работе с этим и аналогичными проектами

- [ ] **Никогда не доверять размеру данных в `localStorage`:** любое сохранение в `localStorage` ОБЯЗАНО быть обернуто в `try...catch`.
- [ ] **Никогда не хранить тяжелый бинарный контент (Raw Base64) в `localStorage`:** для больших объемов использовать `IndexedDB` либо клиентское сжатие картинок.
- [ ] **Всегда использовать `ErrorBoundary` в React-приложениях:** пользователи не должны видеть пустой экран при локальном сбое в одном компоненте.
- [ ] **Проверять типы и `undefined` при фильтрации облачных коллекций:** данные из NoSQL баз могут содержать неполные схемы.
- [ ] **Следить за автоматическим CI/CD:** после пуша в ветку `main` GitHub Actions автоматически собирает и деплоит проект, результат проверяется через хеши в HTML на GitHub Pages.
